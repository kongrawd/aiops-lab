# Evidence — what this runbook rests on, and what it does not

Every step in `SKILL.md` traces to a replication, an engagement observation, or a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it. This file records which is which, so a reader can judge how far to trust each part.

Every step in this document traces to a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it.

**Basis.**

- **Published OpenSearch documentation** for the whole mechanism, which is stated rather than inferred: that query terms are extracted and indexed alongside a saved query and used to select candidates so most saved queries are never evaluated; that terms cannot be extracted from some query types including `wildcard`; that **a saved query whose terms cannot be extracted is evaluated against every percolated document, which slows down percolation as the number of such queries grows**; and that the way to find such queries is to search for the `failed` value in the `extraction_result` subfield. Also for leading wildcards being the most expensive form because matching requires examining all terms in the index, for `allow_leading_wildcard` not applying to regular expressions, for percolate queries being rejected when expensive queries are disallowed, and for the system-index behaviour in which a search can return `200 OK` with zero hits.
- **Published documentation** for every route used: the rule and detector search routes and the `queries[].value` field, the index stats and count APIs, and the CAT routes.
- **Code analysis** of the published implementation, which is the source for the field names and for the candidate-selection behaviour that makes the cost concrete. In `alerting/src/main/java/org/opensearch/percolator/PercolatorFieldMapperExt.java` at `b4334358`, the constants `extraction_result`, `complete` and `failed` are defined, and the candidate query adds a term query on `extraction_result: failed` as a `SHOULD` clause with the comment that documents carrying that term have no extracted-terms field and so always need verifying — which is why every extraction-failed rule is a candidate for every document. The query index's mapping at `core/src/main/resources/mappings/doc-level-queries.json` types its `query` field as `percolator_ext` and carries `monitor_id` and `index` alongside, which is the basis for the field paths in steps 4 and 5.
- **Public upstream issues and changes** for the two competing causes and for rule volume as an independent factor, including the accumulation defect's merged and backported fix and the unmerged query-index cleanup change.

**Replicated.** No step is marked replicated, and `metadata.verification` is `documented` accordingly. The code analysis was performed against a checkout of the development line.

**Not established.**

- **Any quantified relationship between extraction-failed rule count and CPU, latency or throughput.** The documentation gives direction only. This is why magnitude is measured rather than predicted, and why no threshold appears anywhere in this document.
- **Any recommended or maximum rule count per detector.** No published source gives one; the nearest public position is that it would need benchmarking.
- **Whether percolate cost surfaces in the query index's search statistics.** Undocumented, which is why step 6 reports the figure as observed on the query index rather than attributing it to the detector, and why the comparison that would attribute it is named as a separate, write-bearing exercise rather than folded into this read-only procedure.
- **Whether the query index is a protected system index.** The plugin's registered descriptors and the Security Analytics documentation disagree publicly. Both are recorded; step 3 exists because an empty result cannot settle it.
- **Whether query-insight tooling instruments plugin-internal percolate searches.** Undocumented, so no step depends on it.
- **A public artefact for the error-detail correction.** The behaviour change described in *What differs by version* comes from a vendor root-cause analysis delivered during a support engagement, and shipped as a managed-service patch. Searches for a matching upstream issue or change naming the clause limit returned nothing in either plugin repository, so there is no public reference to cite and no version boundary to quote — which is why the check is "read your own error record" rather than "upgrade past version X".
- **A superseded claim to avoid.** A per-monitor field named along the lines of a delete-query-index-every-run flag has circulated as the cause of this load, with the remedy framed as changing a setting. Treat that as unverified: it is a per-monitor document field rather than a cluster or plugin setting, it is absent from the published documentation entirely, no public API sets it on a detector-created monitor, and published source shows it gating an error-recovery retry path rather than an unconditional per-run rebuild. There is no operator-executable procedure there, which is why this runbook does not contain one.

**To raise the level.** Exercise the procedure on a non-production cluster with a deliberately wildcard-heavy rule set: record the extraction-failed ratio, then the search-stats delta with detectors enabled and disabled, and confirm the attribution comparison behaves as step 6 describes. Then set `verification: replicated` and record the version tested.
