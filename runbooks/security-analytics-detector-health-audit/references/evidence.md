# Evidence — what this runbook rests on, and what it does not

Every step in `SKILL.md` traces to a replication, an engagement observation, or a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it. This file records which is which, so a reader can judge how far to trust each part.

`metadata.verification` is `documented`: the sweep has not been exercised end to end as written against a fleet with known-seeded faults.

**This runbook is a router, so its evidence has an unusual shape.** The enumeration and validation steps rest on published documentation. Each *flag*, however, rests on whatever established the fault it points at — and that evidence lives with the runbook that owns the repair. The basis below says which, because a flag is only as trustworthy as the finding it routes to, and two of the five flags are materially better supported than the others.

**Basis.**

- **Published OpenSearch documentation** for every route the sweep calls: the detector search route and the detector rule arrays; the findings search route with `detector_id`, `sortOrder` and `size`, and its `timestamp` and `total_findings` fields; the alerts route with its `alertState` filter and `ERROR` state; the Alerting workflow route and its `enabled` and `last_update_time` fields; the CAT aliases route and its `is_write_index` column; the CAT indices and CAT plugins routes; and the Cluster Settings route with `include_defaults`.
- **Published documentation on system-index protection** for the warning that governs step 2: a caller without access can be served an empty index reader, so a search returns `200 OK` with zero hits even though documents exist, and an empty result must not be read as proof of access. This is the source for validation item 2 being mandatory rather than advisory.
- **Engagement observation, carried from the owning runbooks**, for the two signatures the detector API cannot show. That `monitor_id` and `workflow_ids` are omitted from the detector API response on healthy and broken detectors alike was checked against both states on two separate clusters; `security-analytics-detector-workflow-recovery` records it. That an unset `is_write_index` renders as a literal `-` rather than `false` was observed on multiple live clusters; `security-analytics-alias-write-index-recovery` records it, together with the four-state branch this runbook's step 5 reproduces.
- **A public upstream defect report** for the rule-count flag: the ten-rule evaluation bound, the statement that no error, warning or log entry is emitted, and the statement that the `_execute` route shares the limitation — which is why the pre-flight forbids it.
- **A public upstream defect report** for the alias write-index flag, covering the un-editable-detector consequence.
- **Engagement observation** for the triggers-but-no-rules flag: detectors in that state were identified as the cause of a null-reference failure on the shared overview page, the plugin was reported to have created no monitor or workflow for them, and deleting them resolved it. Recorded during a support engagement, not vendor-documented.
- **Published documentation** for the template-precedence statements in step 6: that `composed_of` entries are applied in listed order with later entries winning, that the index template's own `template` block is applied last and wins, and that two matching index templates resolve by highest `priority` without merging, an absent priority counting as `0`. This is what makes the dotted-key-versus-nested-object form of the same field a non-conflict rather than an open question.
- **Published documentation** for `include_unmapped` defaulting to `false` on the field-capabilities API, which is why step 7 is written around that parameter rather than around a plain mapping read.
- **Code analysis of the published alerting plugin** for the write-index requirement that step 5 and the step 7 caveat rest on: `IndexUtils.getWriteIndex` returns the alias's or data stream's `writeIndex` and returns **`null`** where none is designated, and the per-index read position is held per shard by `initializeNewLastRunContext` in `MonitorFanOutUtils.kt`, keyed by index with a `shards_count`. A detector therefore has nothing to resolve, and nothing to track a position on, where its own alias carries no write index. This is also the basis for the pre-flight warning that a secondary or test alias needs its own write index.
- **Code analysis of the published alerting plugin** for the shuffled fan-out that step 7's per-index caveat assumes: `distributeShards` in `MonitorFanOutUtils.kt` shuffles the eligible node list and assigns shards round-robin, so the percolating node is re-chosen per execution.
- **Code analysis of the published Security Analytics plugin, plus the upstream change that fixes it**, for the template-selection mechanism behind step 6's second and third flags. All of it is one method, `IndexTemplateManager.upsertIndexTemplateWithAliasMappings`, reached from `MapperService.createMappingAction` and skipped entirely when the input is already a concrete index. On the released lines it calls the engine's `findV2Template` on the **input name first** — for an alias, the alias name — and only falls back to the concrete index when that returns null; the concrete index is the alias's write index, or failing that the newest backing index by creation date. It then appends `<alias>*` to whichever template matched, which is what a later save's name lookup sees. The change that removes this skips the name lookup for an alias input, suppresses the pattern append, and fails a save that would attach to another input's plugin-owned template. **Both routes are named in the change's own description** — a second alias whose name starts with the first matching the first's template, and an alias whose backing indices were renamed — and that description states the bug was reported from the field. The change is merged on the development line and the 3.10 branch and **is not backported to any released line**, which is the basis for the version row in `SKILL.md`.
- **Code analysis, confirmed against the development line**, for the replacement-not-merge behaviour behind step 6's first flag: `upsertComponentTemplate` builds a `ComponentTemplate` from the mappings of the request alone, resolved against a single concrete index, and puts it without reading the existing one back. A public change to merge rather than replace was opened and **closed without being merged**, so this behaviour is present on every line including the one carrying the selection fix.
- **Published managed-service documentation** for the remedy step 6 recommends: that the plugin adds its component template to the `composed_of` list of the index template matching your indexes, that mappings under `template.mappings` are applied after `composed_of` so a field alias declared in your own index template wins, that declaring one for every field name your rules use means a new index never depends on the plugin-managed component template, and that **rules whose fields are missing from the index are skipped without an error being reported**. This is also the only public documentation of the `composed_of` attachment at all.
- **An artefact capture from a live cluster** corroborating two details of the mechanism independently of the account that explained it, and predating it: a raw index-template read showing `index_patterns` carrying both the log source's own pattern **and** a second entry of the `<alias>*` form, a `composed_of` holding exactly the plugin's alias-mappings component, and `priority: 0`. The appended pattern and the effective priority of zero are exactly what the code produces, observed in template state rather than inferred from it.
- **Engagement observation** for the remaining two step 6 flags and for the last-save-wins behaviour where two detectors share one alias, which was reproduced by the engineering team on a 3.7 line, as was the narrower case of one rule field mapped to different log fields by two detectors. The alias-spanning-two-log-sources flag rests on an engagement account plus the documented recommendation of separate detectors per log type.
- **The replacement-not-merge behaviour is the best-attested claim in step 6.** It is stated independently six times across two engineers in the engagement record, reproduced on a 3.7 line, and confirmed by code reading and by the managed-service documentation's own framing of where field aliases come from. Where this runbook's claims are ranked by strength, this is the top of the list and the wrong-template flags are below it.

**Replicated.** No step is marked replicated. What has been observed in practice, short of a controlled sweep:

- The detector API omitting `monitor_id` and `workflow_ids` on both healthy and broken detectors, on two clusters.
- `is_write_index` rendering as `-`, and the single-member-explicitly-`false` state being a genuine third failure mode rather than a variant of the first.
- A `size=0` findings request returning an empty array beside a non-zero total.
- A plugin-internal index returning zero hits for a caller without access while holding documents.
- Detectors with triggers and no rules breaking the overview page for every detector.

**Not established.**

- **Whether this flag list is complete.** It is the union of the states the shipped sibling runbooks establish, which is a record of what has been found, not a proof that nothing else is silent. A detector can fail in a way nobody has yet characterised, and this sweep would report it clean. Treat a clean result as "none of the known silent states", not as "healthy".
- **~~The code path that selects the index template to carry the alias component.~~** *Resolved.* The path was read and the mechanism is now code analysis plus an upstream change — see the basis above. Three things the reading added that the engagement account did not have: the fallback target is the write index or the newest backing index rather than any member; the engine consults `priority` when several templates match, with the plugin's own template created at an effective priority of `0` so any operator template with an explicit priority outranks it; and on equal priority the winner follows map iteration order, so a tie is not deterministic. The practical consequence for this runbook is unchanged — resolve the source template from a member index name — but a reader comparing templates should know a tie exists and is arbitrary.
- **Whether a tie between two equally-prioritised matching templates is stable across calls.** The winner follows map iteration order with a strict greater-than comparison, so it is not ordered by name or by age and need not be stable. Step 6 reports the mismatch rather than predicting which template wins, so the procedure does not depend on this — but an automation that asserts a particular winner would be unsound.
- **Step 6's first and second flags are independent mechanisms, and the source material never reconciled them.** The account of a *shrinking* component template on the correct index template, and the account of a correctly populated one landing on the *wrong* index template, were given five days apart by the same engineer with no reference between them, and nothing in the record relates them. They are kept as separate flags here because they have separate causes, separate signatures and separate repairs — but a reader should know that no single source asserts both, so a detector could carry either, both, or one presenting as the other.
- **How much of the engagement record was reachable.** The correspondence thread was read in full and is known complete. The worklog thread was not: roughly a hundred of an estimated two hundred and fifty entries were retrievable with the available tooling, and one unreachable entry is cited elsewhere in the record as containing a raw index-template body — the single most likely place for further evidence on the appended pattern. So the engagement half of this runbook's basis is a partial read of the record, and the code analysis is what carries the mechanism.
- **A recommendation inside the engagement record that was never settled there.** Whether field aliases should be declared in the operator's own index template, or left to the plugin's component template, was answered three different ways across the record and never resolved. This runbook follows the managed-service documentation, which states the case for declaring them yourself, and treats the disagreement as closed by that rather than by the record.
- **Whether a plugin-owned component attached to an operator-created template is validated at all.** It is not, on either side of the version boundary: the ownership guard added by the upstream change fires only when the matched template is plugin-owned and belongs to a different input. A save that resolves to an operator-created template is accepted with no check that it is the template creating the alias's indices. So step 6's second flag can fire on a build carrying the fix, for an operator-created template, and that case has no upstream guard.
- **What a short alias component template proves on its own.** A count below the detector's mapped-field count is a flag, not a diagnosis: a field alias legitimately absent because its target base field is absent renders the same as one dropped by a replacing save. Step 7 is what separates them, and only for the index it reads.
- **Whether the count of concrete query indexes can be compared against the enabled-workflow count.** It cannot, and a flag of that shape was considered for this sweep and withdrawn. Code analysis of `DeleteMonitorService.deleteDocLevelMonitorQueriesAndIndices` shows a monitor holds a `sourceToQueryIndexMapping` and iterates it per source index, so **one monitor legitimately owns several query indexes**, and a count exceeding the workflow count is expected rather than evidence of orphaning. A sound orphan check would have to establish that a query index holds no `monitor_id` matching a live monitor, which is a search against a hidden plugin-owned index and so is subject to the scrubbed-read problem in step 2. Query-index sprawl is sized by `security-analytics-rule-cost-audit` instead.
- **Whether the configuration-index hit count should equal the detector API count.** Step 2 instructs you to record a disagreement rather than reconcile it, because no published source states the relationship between the two sets. A difference might mean an incomplete read, a stale configuration document, or a detector the API will not return to you — and nothing available distinguishes these.
- **What a non-advancing findings timestamp means on its own.** It cannot separate "nothing matched, correctly" from "nothing could match". That is precisely why step 4 routes to `security-analytics-detector-mapping-audit` instead of concluding. Note also that detectors evaluate documents by arrival rather than by a timestamp window, so a quiet detector on back-dated data is not thereby faulty.
- **Which specific rules are affected where the rule-count flag fires.** The discarded evaluation results leave no record, so no procedure can name them. The flag means the whole rule set of that detector is unverified coverage, not that the first ten are safe.
- **Two flagged states have no owning runbook** — triggers-but-no-rules, and a data source that returns `index_not_found_exception`. Both resolutions are operator decisions (delete, or repoint) rather than procedures, so this runbook reports them and stops. If either acquires a procedure, the route belongs here.
- **Whether a detector reads every in-scope index behind its alias or only the alias's write index.** Two engineering analyses available to this review disagree, and the choice would change whether step 5 needs to inspect every member. The conflict is recorded in `security-analytics-rule-cost-audit/references/rule-patterns.md`. Code analysis narrows it without closing it: the alerting plugin exposes **both** paths — `IndexUtils.getWriteIndex`, which resolves an alias or data stream to its single write index and returns `null` where none is designated, and `IndexUtils.resolveAllIndices`, which expands to every concrete index. Which one governs a scheduled per-document evaluation was not traced through `DocumentLevelMonitorRunner` for this review. So the write-index requirement is settled — an alias with no designation resolves to nothing on that path — while the scope question is not. This sweep does not depend on the answer: it reads the designation rather than inferring scope from it, and step 7 instructs reading every member rather than assuming parity.
- **The size of the rollover window step 5 warns about.** It is visible only during the rollover, so an arbitrary-hour sweep cannot measure it, and this runbook does not claim to. It names the condition and routes onward.

**To raise the level.** Exercise the sweep on a non-production cluster carrying one deliberately seeded instance of each flag, then confirm the sweep flags exactly those and nothing else, and that every validation item passes. That last part is the point: a sweep that finds the seeded faults but cannot demonstrate its own reads were complete has not been verified. Then set `verification: replicated` and record the version tested.

The seeds for steps 1 to 5: a detector saved with both rule arrays empty; an alias given a second member with the flag unset; a detector carrying twelve rules; a detector pointed at a deleted index.

The seeds for steps 6 and 7, each of which also exercises the mechanism rather than only the check:

- **Two detectors on one alias, with different field-mapping sets.** Save the second, then read the component template. Expect the first detector's exclusive aliases to be gone, and the first detector to carry a rule-field shortfall in step 7 while still reporting healthy.
- **A prefix collision.** Create aliases whose names share a leading substring, save a detector on the shorter name, then save one on the longer, and read which template carries each component.
- **A renamed member index.** Point an alias at indices created by a template whose patterns no longer match them, save the detector, then roll over and read the new index's aliases.
- **A rule field absent from the source.** Attach a rule referencing a field the index does not carry, then confirm step 7 returns that field under `unmapped` and that no error alert is raised for it.

The template-selection path has been read, so the seeds above are now the whole of what is outstanding for step 6. Two of them are worth running specifically against the version boundary: seeding a prefix collision on a build **with** the upstream change should produce no new misattachment for an alias input but should still reproduce it for a data-stream input, since the pattern append is suppressed only for aliases; and an alias left misattached across an upgrade to that build should make the next field-mappings save **fail** rather than succeed, which is the pre-flight warning this runbook now carries and the single claim in it most likely to surprise an operator.
