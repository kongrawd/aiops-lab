# Evidence — what this runbook rests on, and what it does not

Every step in `SKILL.md` traces to a replication, an engagement observation, or a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it. This file records which is which, so a reader can judge how far to trust each part.

**Basis.**

- **Published engine documentation** for the filter semantics — `include` matching any value, `exclude` refusing any, `require` demanding all, and the rule that shards are allocated only to nodes satisfying all active filters; for `null` as the documented reset value and the all-or-nothing behaviour of a settings request containing an unupdatable setting; for reading effective settings with defaults included; and for the allocation-explain route, its decider output, and the documented role of the `filter` decider in applying index routing-allocation settings.
- **Published managed-service documentation** for the `ShardMovementBlocked` validation issue, its non-overridable status, and its stated remedy of removing shard allocation filters from all affected indexes; for pinned shards causing migration to get stuck and filters leaving shards unassigned for want of eligible nodes; for the keys published as the ones to check; for the divergent handling of `index.blocks.write` on a managed domain and the use of `index.blocks.read_only` instead; and for the restriction of cluster-settings writes to an enumerated allowlist.

**Replicated in part, with a negative outcome that is itself the most useful finding.** `metadata.verification` stays `documented`, because the end-to-end claim — that clearing the filter makes the shard movable — has not been confirmed. What *has* been observed in a support engagement: the settings read, the clear-to-`null` write returning `acknowledged`, and a filtered read confirming the key absent all behaved as written. The shards did not then move. So the commands are exercised and the promised effect is not, which is why step 4 now carries an explicit exit instead of a retry loop.

Also observed: the wildcard form being rejected as described in step 3, and the responsible keys genuinely present on both application indexes and plugin-owned system indexes.

**Not established.**

- **A live conflict over `index.routing.allocation.include._tier_preference`, kept visible rather than resolved.** First-party product tooling flags indexes carrying custom routing-allocation attributes — naming this attribute in its own resource table — and advises that such settings "can prevent successful blue-green deployments during domain updates", recommending their removal. That is a published first-party advisory and it is why operators are told to clear the key. Set against it: the attribute is absent from the published built-in attribute list, and code analysis of the published implementation indicates it cannot block through the index-filter decider at all. And in the one recorded application of the remediation, clearing it did not unblock the deployment. **Both statements stand.** The advisory says "can prevent", not "blocked this"; it does not establish a mechanism. Clear the key — it is cheap, reversible and first-party-recommended — but do not treat it as the established cause, and take step 4's exit when it does not help.
- **The superseded framing to avoid.** Treat "strip this attribute and the upgrade will proceed" as unverified for this engine. The attribute is absent from the published list of built-in allocation attributes, which names `_name`, `_host_ip`, `_publish_ip`, `_ip`, `_host`, `_id` and `_tier`. It appears in the published machine-readable API schema with no behavioural description. And **code analysis of the published implementation contradicts the causal claim**: the index-filter decider passes all three filter groups through a helper that strips every key prefixed `_tier` before evaluating them, returning nothing where that leaves the group empty — identical when read at several release tags and on the development line — so an index whose only include filter is that attribute has no index filter left to block it. The attribute *is* documented in a related engine, where it is described as capable of conflicting with other allocation settings and preventing a shard from allocating, which is the likely origin of the advice. Guidance written for one engine did not transfer.
- **Whether clearing a filter will start relocation on any given cluster,** and how much. This depends on current shard placement and load, which is why step 5 measures rather than predicts and why the impact section flags the two-way cost.
- **A documented column list for `_cat/shards`.** The route and its column-selection parameter are documented but the column names are not enumerated, so the unassigned-reason column rests on its use in published guidance. The allocation explanation is the authoritative source for that reason.
- **Plugin-owned system indexes as a blocker, and the consequences of deleting them.** No public coverage. Reach out instead.

**To raise the level.** Exercise the procedure on a non-production index: set a require filter naming a node that does not exist, confirm the shard becomes unassigned and that step 1 names the `filter` decider, then clear it and confirm the decider flips and the shard assigns. Then set `verification: replicated` and record the version tested.
