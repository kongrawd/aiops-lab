# Evidence — what this runbook rests on, and what it does not

Every step in `SKILL.md` traces to a replication, an engagement observation, or a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it. This file records which is which, so a reader can judge how far to trust each part.

Every step in this document traces to a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it, so nothing here is offered on the strength of how the system appears to work.

**Basis.**

- **Published OpenSearch documentation** for every API call: the detector search route and the detector `enabled` field; the workflow get and update routes, the workflow `enabled` field, the documented `PUT` body, and the definition of a workflow ID as a composite monitor's monitor ID; the findings search route with its `detector_id` and `sortOrder` parameters and the `timestamp` field; and the Security plugin's system index behaviour, which states that a search against a protected index can return `200 OK` with zero hits even though matching documents exist.
- **Code analysis** of the published implementation for two points the documentation does not cover. That evaluation fans out rather than running on one node is visible in `alerting/src/main/kotlin/org/opensearch/alerting/DocumentLevelMonitorRunner.kt`, which issues a fan-out request per target and aggregates the responses, handled by `TransportDocLevelMonitorFanOutAction` — so "which node is this detector on" is the wrong question to ask of a stale workflow. That the detector object carries `workflow_ids` linking it to its workflow is visible in the Security Analytics detector model, which serialises the field unconditionally; this is why `workflow_ids: null` is a readable state distinct from an empty list, and it is not on the documentation site.

- **Engagement observation plus reported analysis** for one point that published code reviewed here does not cover: that a disable writes to the detector and to the workflow in sequence and can end before the workflow write under load. Two independent engagement records describe it in the same terms — the enabled flag reaches the workflow only at the final stage of a multi-stage update, and a failure at an earlier stage leaves the detector marked in error while its workflow keeps executing on schedule, with load named as the likely trigger. One of those records states the operational consequence directly: **console state is not authoritative for whether a detector has stopped.** That is the justification for this runbook existing, and it is stronger than documentation-only — but it remains engagement-recorded rather than vendor-documented. The ordering and the timeout are the reported mechanism. This runbook does not depend on them — step 2 branches on the observed disagreement and its timestamp, whatever produced it — so the claim appears in Impact as the reported failure path and nowhere in the procedure. Confirming it would need code analysis of the detector-indexing path in the Security Analytics implementation, which this review did not cover.

**Replicated in part.** `metadata.verification` stays `documented` because the sequence has not been run end to end as written. What is engagement-observed: the disagreement itself — a detector presenting as stopped while its workflow continued executing — and the fact that it was found by reading the workflow rather than the console. The repair write and its read-back are not recorded as executed anywhere available to this review, so steps 3 and 4 are the least exercised part of this document and the first thing to try on a non-production detector.

**Not established.**

- **Whether a timeout is the only path to a stale workflow.** The reported mechanism is a timeout under load. This runbook detects the disagreement whatever produced it, which is why step 2 branches on the timestamp rather than on a presumed cause.
- **The response shape of `GET _plugins/_alerting/workflows/{workflow_id}`.** The documentation gives the `PUT` body but no `GET` response example, so step 3 instructs you to read the shape you received rather than asserting one.
- **Whether the behaviour holds below 3.7.** The workflow APIs exist from 2.9, so the detection path should apply there; the timeout behaviour was reported on 3.7 only.
- **A superseded method to avoid.** Enumerating this state by querying `.opendistro-alerting-config` directly is circulated and does not work, and it fails silently rather than with an error. It is called out in *Before you start* for that reason.

**To raise the level.** Exercise steps 1 to 4 against one non-production detector, confirm the step 4 read-back reflects the step 3 write and that validation 2 stops advancing, then set `verification: replicated` and record the version tested. Exercising it on a loaded cluster would additionally confirm the reported timeout path.
