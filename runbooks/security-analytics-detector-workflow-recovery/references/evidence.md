# Evidence — what this runbook rests on, and what it does not

Every step in `SKILL.md` traces to a replication, an engagement observation, or a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it. This file records which is which, so a reader can judge how far to trust each part.

Every step in this document traces to a reputable source. A step resting on inference is reason to leave a procedure unwritten rather than to label it.

**Basis.**

- **A public upstream defect report**, open, filed by an author the tracker records as a repository collaborator, carrying a code-level root-cause account: a save with empty rule arrays deletes the workflow and sets the reference to an empty list, and a subsequent save that re-adds rules never recreates it. It is the source for the stated scope, for the absence of a user-visible error, for the orphaned-workflow alternative outcome, and for deletion and recreation being the only recovery. It also records the re-adding-rules attempt and its failure, which is why step 4 tells you not to try it.
- **Code analysis** of the published implementation, which corroborates both halves independently of the report: in the detector-indexing transport action, the branch taken when no monitors remain deletes the workflow and then clears the detector's workflow list; the workflow-maintenance step is guarded by a test that reads that same list, with no branch that creates a workflow when the list is empty. The workflow-not-found message, its advice to delete and recreate, and the fact that it is raised only for an enabled detector are all in that same source, and the message is asserted in the repository's own REST integration tests — so it is an intentional, tested error path rather than an incidental log line.
- **Published OpenSearch documentation** for the detector-and-workflow relationship and the `enable_workflow_usage` setting that governs it; for stopping and starting a detector as the supported way to pause one, and the `enabled` field behind it; for the statement that at least one rule must be specified; and for every route used — detector search, get, create and delete, the alerting workflow get route, and the alerts and findings routes.

**Replicated.** No step is marked replicated, and `metadata.verification` is `documented` accordingly.

**Not established.**

- **Whether findings and alert history remain retrievable after recreation.** No public source addresses it, and no engagement in the record performed the decisive before-and-after retrieval. What is established: recreation issues a **new detector identifier**; alerts and findings carry `detector_id` as a first-class field and the read APIs filter on it, so prior history is not reachable under the new identity; the preserved-item list for a service-performed recreation covers rules, triggers, schedule and notification destination and **does not mention history**, with a fresh query index provisioned; and before deletion, history was still retrievable from a broken detector, so breakage alone does not cost it — deletion is the step that matters. Counter-signal worth keeping: the raw alert-history indexes were continuous across an incident window, so the underlying documents may persist on disk and be reachable by direct index search even when the detector-scoped API path can no longer resolve them. **Plan on prior findings and alerts becoming unreachable through the detector-scoped APIs, and export anything you need before deleting.**
- **Maintainer confirmation of the defect.** The public report carries only a triage acknowledgement. The code analysis corroborates the mechanism, which is why this runbook exists; the absence of maintainer confirmation is why the stated version scope is presented as the reporter's claim.
- **Any fix or target release.** The defect is present on the development line and the report's two candidate designs are unimplemented. Do not plan around an upgrade.
- **`workflow_ids` as a documented API field.** It is absent from the published Detector API page and established from source and the defect report, which is why step 1 treats a missing key and an empty array alike.
- **A superseded claim to avoid.** A separate failure of the Security Analytics overview page was attributed to detectors having triggers and zero rules. That attribution is not publicly sourceable, and the published findings code path argues against it, because a detector with no rules contributes no monitor identifiers to the mapping where the failure occurs. This runbook therefore makes no claim about the overview page, and an operator seeing that failure should not treat zero-rule detectors as the established cause.

**To raise the level.** Exercise the whole procedure on a non-production detector: save it with empty rule arrays to induce the state, confirm the signature in step 1, then recover through steps 3 to 5 — and while you are there, record whether findings written under the original identifier remain retrievable, which would close the largest open question in this document. Then set `verification: replicated` and the version tested.
